The AI Open Systems Interconnection (AOSI) Reference Model: A Seven-Layer Stack for Generative AI Execution

Abstract

Generative AI systems execute across a deep, heterogeneous stack: client applications and APIs, orchestration gateways, retrieval pipelines, inference-serving engines, transformer model architectures, compiler and runtime frameworks, and accelerator hardware. Each tier has its own abstractions, tooling, and telemetry, but there is no shared reference model that names the tiers, defines the data state exchanged at each boundary, and assigns responsibility for performance, correctness, and security.¶

This document describes the AI Open Systems Interconnection (AOSI) Reference Model, a seven-layer conceptual stack for generative AI execution, from silicon (Layer 1) to the application (Layer 7). For each layer, it defines purpose and scope, core components, the data-state transformation performed, interfaces to adjacent layers, observability signals, and characteristic failure modes. It also describes a layer-oriented diagnostic method for isolating bottlenecks, places security considerations at the layer where each threat materializes, and outlines future work on agentic workflows, distributed inference, and cross-layer optimization. The model is informational; it defines no protocol.¶

1. Introduction

1.1. Architectural Fragmentation in Generative AI

The execution of a single generative request traverses at least seven distinct engineering disciplines. In practice, these disciplines are separated by organizational boundaries (application, platform, machine learning, and infrastructure teams), by tooling boundaries (application performance monitoring, MLOps dashboards, GPU profilers, and data-centre monitoring), and by vocabulary boundaries ("prompt", "batch", "graph", "kernel", "rail").¶

This fragmentation produces four systemic deficiencies:¶

  1. Non-attributable performance: End-to-end latency is the composition of queueing, retrieval, prefill, decode, kernel execution, and memory transfer. Without a layered decomposition, a regression in one tier is observed only as an aggregate symptom in another.¶

  2. Implicit contracts: The interfaces between tiers (what a "prompt" contains when it reaches the serving engine, what a "batch" guarantees to the model, what a "graph" promises to the device) are defined by individual products rather than by a stable reference.¶

  3. Mis-located controls: Security, privacy, and governance controls are frequently specified as "AI controls" without regard to the tier at which the threat materializes. This leaves gaps (for example, grounding-data integrity) and duplications (for example, output filtering at several tiers with inconsistent policy).¶

  4. Non-transferable expertise: Engineers lack a common frame to describe where a behaviour originates, which slows incident response and design review.¶

1.2. Contribution of This Document

The OSI Basic Reference Model [ISO7498-1] [X.200] demonstrated that a layered decomposition, with explicit service boundaries and named protocol data units, enables independent evolution of layers, precise fault localization, and a shared professional vocabulary. AOSI applies the same method to generative AI execution. Specifically, this document:¶

  • defines seven layers with explicit scope boundaries (Section 5);¶

  • defines a canonical data-state chain (JSON Payload, Enriched Prompt, Vector Chunks, Batched Tensors, Hidden States, Tensor IR, Silicon Voltages), analogous to OSI protocol data units (Section 4.3);¶

  • describes a request lifecycle down and up the stack (Section 6);¶

  • describes a layer-isolation diagnostic method (Section 7);¶

  • places security considerations at the layer where each threat materializes (Section 11);¶

  • positions AOSI against prior reference models, industry stack models, and security frameworks (Section 9); and¶

  • reserves Layers 8 and 9 and a cross-layer optimization plane for future work (Section 8).¶

This document is derived from AOSI-RFC-0001, Version 1.2.1 [AOSI-RFC-0001], a self-published document by the same author; see Appendix "Origin of This Document".¶

1.3. Scope and Non-Goals

In scope: inference-time execution of generative models (primarily autoregressive transformer language models and, by extension, multimodal models) from client request to device execution and back.¶

Out of scope for this revision:¶

  • Training and fine-tuning pipelines, except where they share Layers 1-3 (see Section 8.2).¶

  • Data governance processes upstream of the Layer 5 index; ingestion pipelines are referenced only at their interface.¶

  • Any wire protocol, API schema, or certification regime. AOSI is a reference model, not a protocol.¶

  • Endorsement of any product. Named technologies are illustrative examples of components that occupy a layer.¶

2. Conventions and Terminology

2.1. Requirements Language

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

In this document, these key words apply to descriptions and implementations that claim alignment with AOSI, not to any product.¶

2.2. Terminology

Layer (Ln):

A tier of the AOSI stack with a defined scope, data state, and set of interfaces. L1 is closest to silicon; L7 is closest to the user.¶

Data State:

The canonical representation of a request (or response) as it crosses a layer boundary. Analogous to an OSI protocol data unit.¶

Boundary:

The interface between two adjacent layers, written Ln/Ln-1. A boundary is where a data state is handed off and where telemetry SHOULD be emitted.¶

Down-path:

Transformation of a request from L7 toward L1 (request ingestion, retrieval, prefill dispatch).¶

Up-path:

Transformation of results from L1 toward L7 (logits, sampling, detokenization, streaming).¶

Prefill:

The forward pass over all prompt tokens that populates the KV cache and produces the first output logits. Typically compute-bound.¶

Decode:

The iterative forward passes after prefill, producing one token per step (or k tokens per step with speculative decoding). Typically memory-bandwidth-bound at low batch sizes.¶

KV cache:

Per-sequence storage of attention key and value tensors for prior tokens, which avoids recomputation during decode.¶

TTFT:

Time to First Token: the time from request receipt to the first output token emitted to the client.¶

TPOT / ITL:

Time per Output Token / Inter-Token Latency: the mean (or distribution) of intervals between successive output tokens.¶

E2E latency:

End-to-end request latency, approximately TTFT + (N_output - 1) x TPOT for a streamed response.¶

Goodput:

Throughput of requests that meet their latency service-level objectives (SLOs).¶

Span:

An OpenTelemetry unit of traced work. AOSI-aligned tracing attributes each span to exactly one layer.¶

Tensor IR:

Any intermediate representation of a computation graph or kernel below the framework API (for example, TorchFX/Inductor graphs, StableHLO, MLIR dialects, or PTX).¶

2.3. Notation

Layer references use the form L1-L7. A boundary is written L5/L4. Thresholds given as "illustrative" in Section 7 are examples for exposition, not recommended values.¶

3. Design Principles

P1 - Single responsibility per layer:

Each layer MUST have one primary function. A component that spans layers (for example, a serving engine with built-in kernels) SHOULD be described as occupying each layer separately.¶

P2 - Named data state at every boundary:

Every boundary MUST have a defined data state, so that it can be captured, inspected, and measured.¶

P3 - Adjacency of interfaces:

A layer SHOULD interact only with its immediate neighbours. Cross-layer shortcuts (for example, an application pinning a GPU) MUST be documented as explicit cross-layer couplings.¶

P4 - Observability by construction:

Each layer SHOULD emit telemetry at its boundaries that is attributable to that layer, enabling isolation (Section 7).¶

P5 - Technology neutrality:

Layer definitions MUST NOT depend on a specific vendor, framework, or accelerator.¶

P6 - Cost gradient awareness:

Latency and computational cost increase toward lower layers; semantic abstraction and policy surface increase toward upper layers. Optimizations SHOULD be evaluated against this gradient.¶

P7 - Security at the point of materialization:

Controls SHOULD be placed at the layer where a threat materializes, with defense in depth at adjacent layers where justified.¶

4.1. The Stack

Figure 1 shows the seven layers, their primary functions, and the data state each layer produces on the down-path.¶

L5 is normally traversed on the down-path only. On the up-path, results from L4 return to L6 for output policy and then to L7 for delivery.¶

4.3. The Canonical Data-State Chain

5. Layer-by-Layer Description

Each layer is described with six subsections: Purpose and Scope, Core Components, Data-State Transformation, Interfaces, Key Metrics and Observability Signals, and Failure Modes. Layers are presented from L7 down to L1, following the down-path of a request.¶

5.1. Layer 7: Application Layer

5.1.1. Purpose and Scope

L7 is the point of end-user interaction and UI rendering. It captures user intent, serializes it into a machine request, and renders the streamed response. L7 owns user experience, client-side session handling, authentication of the end user to the application, and presentation of results (including citations and tool outputs). L7 MUST NOT embed model-specific prompt construction logic that belongs to L6.¶

5.1.2. Core Components

  • Chat UIs, IDE assistants, web and mobile applications, copilots, and end-user-facing agents.¶

  • API clients and SDKs issuing OpenAI-compatible (or equivalent) JSON requests.¶

  • Streaming transports: Server-Sent Events (SSE), WebSockets, and gRPC streams.¶

  • Client-side rendering: Markdown and code rendering, citation display, partial-output handling, and cancellation.¶

5.1.3. Data-State Transformation

Down-path:

Input is user intent (text, files, images, UI actions). Output is the JSON Payload, for example {model, messages, tools, temperature, max_tokens, stream}.¶

Up-path:

Input is streamed response chunks (token deltas, tool-call deltas, finish reason, usage). Output is rendered output to the user.¶

5.1.4. Interfaces

  • L7 to L6: HTTP(S) or gRPC request carrying the JSON Payload, end-user identity, and session identifiers.¶

  • L6 to L7: Stream of response chunks, terminal status (finish_reason), usage accounting, and policy outcomes (for example, refusal codes).¶

5.1.5. Key Metrics and Observability Signals

Client-perceived TTFT; client-perceived inter-token latency; time to render; request error rate by status class; cancellation and abandonment rate; payload size; client-side span (aosi.layer=7).¶

5.1.6. Failure Modes

Client timeouts shorter than server SLOs; buffering proxies that defeat streaming (whole-response delivery); malformed or oversized payloads; retry storms amplifying load on lower layers; rendering stalls misattributed to model latency.¶

5.2. Layer 6: Orchestration and Gateway

5.2.1. Purpose and Scope

L6 governs routing, safety, state, and context management. It authenticates and authorizes the calling application, enforces quotas, selects the target model or endpoint, applies prompt templates and system policy, maintains conversation state and memory, invokes L5 when grounding is required, and applies input and output guardrails. L6 is the policy enforcement point of the stack.¶

5.2.2. Core Components

  • API gateways and AI gateways (authentication, rate limiting, quota, routing, failover, semantic or response caching).¶

  • Orchestration frameworks such as LangChain, LlamaIndex, and equivalent workflow engines.¶

  • Prompt templates and chat templates; system-prompt management.¶

  • Guardrails: input classifiers, PII redaction, jailbreak and prompt-injection detection, output moderation, and schema validation for structured output.¶

  • Session and memory stores (conversation history, summarization of long histories).¶

  • Model routers (cost-, latency-, or capability-based selection).¶

5.2.3. Data-State Transformation

Down-path:

Input is the JSON Payload. Output is the Enriched Prompt: an ordered message sequence of system policy, template, session state or memory, an optional grounding slot, and the user turn, with the routing decision and policy verdicts attached.¶

Up-path:

Input is the detokenized text stream from L4. Output is policy-filtered, schema-validated response chunks to L7.¶

5.2.4. Interfaces

  • L6 to L5: Retrieval query (raw or rewritten), tenant or ACL filter, top-k, and score thresholds.¶

  • L5 to L6: Ranked Vector Chunks with provenance metadata.¶

  • L6 to L4: Final prompt (text or pre-templated messages), sampling parameters, priority or SLO class, and routing target.¶

  • L4 to L6: Token or text stream, usage, and finish reason.¶

5.2.5. Key Metrics and Observability Signals

Gateway overhead latency; guardrail latency (input and output); routing decisions by model; response or semantic cache hit rate; policy-violation and refusal rates; prompt token count after enrichment; rate-limit rejections; span aosi.layer=6 with child spans per guardrail and template step.¶

5.2.6. Failure Modes

Prompt bloat from unbounded history (pushing load onto L4 prefill); guardrail latency dominating TTFT; streaming defeated by output moderation that buffers the full response; routing to an overloaded or wrong-capability endpoint; template mismatch with the model's chat template causing quality regressions; prompt injection passing policy checks.¶

5.3. Layer 5: Retrieval and Knowledge (RAG)

5.3.1. Purpose and Scope

L5 performs context injection, semantic search, and grounding. It converts a query into an embedding, searches one or more indexes, reranks and filters candidates, and returns chunks that L6 merges into the Enriched Prompt. L5 owns the retrieval index at query time and the integrity of grounding data as served. Index construction (ingestion, chunking, and embedding at write time) is referenced at its interface only.¶

5.3.2. Core Components

  • Vector databases and approximate-nearest-neighbour (ANN) indexes (for example, Pinecone or Milvus; HNSW, IVF, or PQ index types).¶

  • Embedding models (query and document encoders).¶

  • Chunkers and document parsers (write-path interface).¶

  • Hybrid retrieval (lexical BM25 plus dense), metadata filters, and ACL-aware retrieval.¶

  • Rerankers (cross-encoders) and context compressors.¶

5.3.3. Data-State Transformation

Down-path:

Input is the retrieval query from the Enriched Prompt (text and filters). Output is Vector Chunks: query embedding, top-k candidate vectors, and reranked retrieved chunks (text, score, source URI, version, ACL tag), merged into the prompt context.¶

5.3.4. Interfaces

  • L6 to L5: Query, filters, k, and budget (tokens or time).¶

  • L5 to L6: Ordered chunks with scores and provenance; empty-result signal.¶

  • L5 to L4 (embedding inference, optional): Embedding models MAY themselves be served by an L4 engine; such calls MUST be traced as nested L4 spans within the L5 span.¶

5.3.5. Key Metrics and Observability Signals

Embedding latency; ANN search latency (p50/p95/p99); rerank latency; recall@k or nDCG against an evaluation set; empty-result rate; retrieved-token count contributed to the prompt; index freshness (age of the newest indexed document); span aosi.layer=5.¶

5.3.6. Failure Modes

Retrieval lag under load (ANN index not memory-resident, cold caches, network hops to a managed service); low recall from embedding-model mismatch or poor chunking; context dilution from excessive k; stale index; ACL leakage across tenants; poisoned or adversarial documents (see Section 11).¶

5.4. Layer 4: Inference and Serving

5.4.1. Purpose and Scope

L4 manages model execution as a service: tokenization, admission control, scheduling, batching, KV-cache management, API-level caching (for example, prefix caching), and sampling orchestration. L4 converts many independent prompts into a sequence of batched forward-pass invocations on L3 and returns tokens as they are produced. L4 is where request-level concurrency meets device-level parallelism.¶

5.4.2. Core Components

  • Serving engines such as vLLM, TensorRT-LLM, Hugging Face TGI, and NVIDIA Triton Inference Server (and equivalents).¶

  • Tokenizers and detokenizers (BPE, SentencePiece).¶

  • Schedulers: continuous (iteration-level) batching, chunked prefill, priority and preemption policies, and prefill/decode disaggregation.¶

  • KV-cache managers: PagedAttention block allocation [PAGEDATTENTION], prefix caching, eviction and swap, and KV quantization.¶

  • Decoding accelerators: speculative decoding (draft models, multi-token heads) and constrained or structured decoding.¶

  • Model replicas and parallelism configuration (tensor, pipeline, or expert parallel degree) exposed to L2.¶

5.4.3. Data-State Transformation

Down-path:

Input is the Enriched Prompt (text or messages). Output is Batched Tensors: token-ID tensors, position IDs, attention metadata (sequence lengths, causal masks), KV-cache block tables, batch-slot assignments, and sampling parameters.¶

Up-path:

Input is logits or probabilities per sequence from L3. Output is sampled token IDs, detokenized into text deltas and streamed to L6.¶

5.4.4. Interfaces

  • L6 to L4: Prompt, sampling parameters, maximum tokens, and priority.¶

  • L4 to L3: Per-iteration batch descriptor and input tensors; KV-cache pointers.¶

  • L3 to L4: Logits (or sampled tokens if sampling is fused); updated KV-cache state.¶

5.4.5. Key Metrics and Observability Signals

Queue time (time waiting before first scheduling); server-side TTFT; TPOT/ITL; prefill and decode throughput (tokens/s); running and waiting request counts; KV-cache utilization; prefix-cache hit rate; preemption and swap counts; batch size per iteration; speculative-decoding acceptance rate; span aosi.layer=4 with child spans for queue, prefill, and decode. Engine metric names vary by product and version.¶

5.4.6. Failure Modes

KV-cache exhaustion leading to preemption, recomputation, or swapping and therefore TPOT spikes; head-of-line blocking from long prefills interfering with decode (mitigated by chunked prefill or disaggregation); over-batching that trades TPOT for throughput beyond the SLO; low prefix-cache hit rate due to non-deterministic prompt prefixes from L6; tokenizer mismatch with the model.¶

5.5. Layer 3: Model and Weight Architecture

5.5.1. Purpose and Scope

L3 is the mathematical representation of tokens and language: the model architecture and its learned parameters. It defines what computation is performed for a given batch: embedding lookup, a stack of transformer blocks (attention, MLP or mixture-of-experts, normalization, residual connections), and the output projection to vocabulary logits. L3 owns numerical representation choices (precision and quantization of weights, activations, and KV cache) as properties of the model artifact.¶

5.5.2. Core Components

  • Token and positional embeddings (for example, rotary position embeddings).¶

  • Transformer blocks: multi-head, grouped-query, or multi-query attention; attention heads; feed-forward/MLP layers; MoE routers and experts; normalization (LayerNorm, RMSNorm); activations (for example, GELU or SwiGLU).¶

  • Weights and their formats: FP16/BF16, FP8, INT8, and INT4 (weight-only or weight-and-activation quantization); adapters (for example, LoRA).¶

  • Output head and logit-processing hooks (temperature, top-p/top-k, repetition penalties) where defined by the model contract.¶

5.5.3. Data-State Transformation

Down-path:

Input is Batched Tensors (token IDs, positions, KV pointers). Output is Hidden States: per-block activations of shape (batch, seq, d_model), attention outputs, expert-routed activations, and the final hidden state.¶

Up-path:

Input is the final Hidden States. Output is logits of shape (batch, vocab), converted to probabilities (softmax) and returned to L4 for sampling.¶

5.5.4. Interfaces

  • L4 to L3: Forward-pass invocation with batch descriptor.¶

  • L3 to L2: The model expressed as a framework program (module graph) with parameter tensors and parallelism annotations.¶

  • L3 to L4: Logits or probabilities and KV-cache writes.¶

5.5.5. Key Metrics and Observability Signals

Parameter count and active parameters per token (MoE); FLOPs per token (prefill versus decode); weight and KV-cache bytes per token; quantization error or perplexity delta versus reference precision; expert load balance (MoE); logit statistics (entropy, NaN/Inf detection); output quality evaluations.¶

5.5.6. Failure Modes

Numerical instability (overflow in low precision, NaN propagation); quality regression from aggressive quantization; MoE expert imbalance causing stragglers; context-length extrapolation failure beyond the trained range; architecture or weights mismatch with the serving configuration (for example, wrong RoPE scaling).¶

5.6. Layer 2: Framework and Runtime

5.6.1. Purpose and Scope

L2 provides low-level math operations, graph compilation, and parallelism. It lowers the L3 model program into executable kernels and collective communication schedules for the target device, manages device memory allocation and streams, and implements tensor, pipeline, data, and expert parallelism. L2 is where model math becomes device programs.¶

5.6.2. Core Components

  • Frameworks: PyTorch (eager and torch.compile/Inductor) and JAX.¶

  • Compilers and IRs: XLA/StableHLO, MLIR, the Triton compiler, TensorRT builders, and TVM-class compilers.¶

  • Kernel libraries: cuBLAS/cuBLASLt, CUTLASS, cuDNN, FlashAttention, and ROCm equivalents (rocBLAS, MIOpen).¶

  • Device runtimes and drivers: CUDA, ROCm, and vendor runtimes for TPUs and other accelerators; CUDA Graphs.¶

  • Collective communication: NCCL and RCCL; parallelism frameworks such as DeepSpeed and Megatron-LM.¶

5.6.3. Data-State Transformation

Down-path:

Input is the Hidden-State computation (module graph and weights). Output is Tensor IR: the captured or lowered graph (for example, FX/Inductor IR, StableHLO, MLIR, PTX/SASS), fused kernels (GEMM, attention, norm, activation), launch configurations, and collective schedules (all-reduce, all-gather, all-to-all).¶

Up-path:

Input is kernel completion and device buffers. Output is output tensors materialized for L3.¶

5.6.4. Interfaces

  • L3 to L2: Framework program and parameters.¶

  • L2 to L1: Kernel launches, memory copies, collective operations over the device interconnect, and driver calls.¶

  • L1 to L2: Completion events, error codes, and hardware counters.¶

5.6.5. Key Metrics and Observability Signals

Kernel time breakdown (GEMM versus attention versus communication); kernel launch overhead and CPU-side gaps; achieved occupancy and arithmetic intensity (roofline position); collective-communication time and overlap with compute; compilation and recompilation events (graph breaks); allocator fragmentation. Typical tools include NVIDIA Nsight Systems and Nsight Compute, PyTorch Profiler, JAX/XLA profilers, and ROCm profilers.¶

5.6.6. Failure Modes

Graph breaks and recompilation causing latency jitter; unfused or sub-optimal kernels; launch-bound execution at small batch sizes (mitigated by CUDA Graphs); collective stalls from topology-unaware placement; memory fragmentation leading to out-of-memory despite free capacity; driver or runtime version incompatibility.¶

5.7. Layer 1: Physical Infrastructure

5.7.1. Purpose and Scope

L1 supplies raw power, silicon math, and interconnects. It comprises the accelerators that execute multiply-accumulate operations, the memory hierarchy that feeds them, the intra-node and inter-node fabrics that connect them, and the power and cooling envelope that constrains them. L1 is where every abstraction above is paid for in joules, bytes, and nanoseconds.¶

5.7.2. Core Components

  • Accelerators: GPUs (for example, NVIDIA H100-class or AMD Instinct-class), TPUs, and other AI ASICs; tensor cores and matrix engines.¶

  • Memory: HBM (for example, HBM3/HBM3e), on-chip SRAM and caches, host DRAM, and NVMe tiers (for KV or weight offload).¶

  • Interconnects: NVLink/NVSwitch (intra-node), PCIe, InfiniBand and RoCE Ethernet (inter-node), and NICs/DPUs.¶

  • Facility: power delivery, power capping, air or liquid cooling, and rack and cluster topology.¶

5.7.3. Data-State Transformation

Down-path:

Input is Tensor IR as executable kernels and transfers. Output is Silicon Voltages: switching activity in tensor cores (MAC operations), HBM read and write transactions, and link signalling, measurable as power draw and heat.¶

Up-path:

Input is physical computation results. Output is bits in device memory, completion events, and hardware counters exposed to L2.¶

5.7.4. Interfaces

  • L2 to L1: Kernel launches, DMA transfers, and collective traffic.¶

  • L1 to L2: Results, interrupts and events, error signals (ECC and Xid-class errors), and telemetry counters.¶

5.7.5. Key Metrics and Observability Signals

Streaming-multiprocessor or compute-unit activity; tensor-pipe activity; HBM (DRAM) bandwidth utilization; memory capacity used; NVLink, PCIe, and InfiniBand throughput and errors; power draw versus cap; temperature; clock-throttle reasons; ECC and hardware error counts. Typical tools include NVIDIA DCGM, nvidia-smi, rocm-smi, fabric managers, and facility BMS/DCIM systems.¶

5.7.6. Failure Modes

HBM bandwidth saturation during decode (memory-bound regime); thermal or power throttling reducing clocks; link degradation causing collective slowdowns; ECC or hardware faults; noisy neighbours under device partitioning (for example, MIG) or shared fabrics; capacity exhaustion forcing offload to slower tiers.¶

6. Request Lifecycle

6.1. Down the Stack: Ingestion, Grounding, and Prefill

  1. L7: The user submits a question in a chat UI. The client issues a JSON Payload with "stream": true.¶

  2. L6: The gateway authenticates the application, enforces quota, selects a model endpoint, runs input guardrails, loads session history, and applies the prompt template. It determines that grounding is required.¶

  3. L5: The query is embedded, the vector index is searched with tenant ACL filters, candidates are reranked, and the top-k chunks with provenance are returned. L6 merges them into the Enriched Prompt.¶

  4. L4: The serving engine tokenizes the prompt, checks the prefix cache, allocates KV-cache blocks, and admits the sequence into the next scheduling iteration, forming Batched Tensors with other in-flight sequences.¶

  5. L3: The prefill forward pass computes Hidden States for all prompt tokens across all transformer blocks and writes keys and values into the KV cache.¶

  6. L2: The runtime executes the corresponding Tensor IR: fused attention and GEMM kernels, plus collectives if the model is sharded.¶

  7. L1: Tensor cores, HBM, and the interconnect execute the work as Silicon Voltages; prefill is predominantly compute-bound.¶

6.2. Up the Stack: Decode and Token Streaming

  1. L3 to L4: Final hidden states are projected to logits; L4 samples the first token. TTFT is fixed at this point (plus up-path transit).¶

  2. L4 to L6 to L7: The token is detokenized and streamed through output guardrails to the client.¶

  3. Decode loop: For each subsequent token, L4 schedules a decode iteration; L3, L2, and L1 execute a single-token forward pass that reads the full KV cache and the weights from HBM. At typical batch sizes, decode is memory-bandwidth-bound, so TPOT is governed primarily by L1 memory bandwidth and L4 batching and KV-cache behaviour.¶

  4. Completion: On a stop condition, L4 frees KV-cache blocks (or retains them for prefix reuse), L6 records usage and policy outcomes, and L7 renders the final state.¶

7. Diagnostic and Troubleshooting Method

7.1. Layer-Attributed Tracing

Packet analysers make network faults tractable by decoding each captured packet layer by layer, so that an engineer can assert which layer misbehaved. AOSI applies the same discipline to generative AI: every request SHOULD produce a trace in which each span is attributed to exactly one AOSI layer and each boundary hand-off is timestamped. Diagnosis then proceeds by decomposition rather than intuition.¶

An AOSI-aligned deployment SHOULD:¶

  1. Propagate a single trace context (W3C Trace Context [TRACE-CONTEXT], for example via OpenTelemetry) from L7 through L4.¶

  2. Tag every span with aosi.layer (Appendix B) and, where available, OpenTelemetry generative AI semantic-convention attributes [OTEL-GENAI] (for example, model name and input and output token usage).¶

  3. Export L4 engine metrics and L1 device metrics on a common time base, labelled with node, device, and replica identifiers, so that request spans can be joined to device telemetry.¶

  4. Capture L2 profiles on demand for representative requests.¶

7.2. Latency Decomposition

End-to-end latency for a streamed request decomposes as shown in Figure 4.¶

The two components isolate different layers:¶

  • TTFT inflated, TPOT normal: look above L4 compute, at L6 overhead, L5 retrieval lag, L4 queueing, or long-prompt prefill.¶

  • TPOT inflated, TTFT normal: look at or below L4 decode, at KV-cache pressure or preemption (L4), batch-size growth (L4), HBM bandwidth saturation (L1), throttling (L1), collective stalls (L2/L1), or buffering output guardrails (L6).¶

  • Both inflated: systemic causes such as overload (L4 queue), device degradation (L1), or retry storms (L7).¶

7.3. Distinguishing Retrieval Lag, KV-Cache Latency, and Memory Bandwidth Saturation

These three causes are routinely confused because each surfaces as "the model is slow". They are separable with the signals below. Thresholds are illustrative only and MUST be calibrated per deployment.¶

7.3.1. L5 Retrieval Lag

Latency signature:

TTFT rises; TPOT is unchanged.¶

Trace:

The aosi.layer=5 span (embed, ANN search, rerank) grows before any L4 span starts.¶

L4 engine metrics:

Queue and KV-cache usage are normal.¶

L1 device metrics:

Normal.¶

Isolation test:

Bypass retrieval (use a fixed cached context of equal token length) and replay. If TTFT recovers, L5 is confirmed.¶

Illustrative trigger:

L5 span p95 greater than 30% of TTFT.¶

Remediation:

Keep the ANN index memory-resident; co-locate the vector database; cache query embeddings; reduce k or rerank depth; parallelize retrieval with other L6 work.¶

7.3.2. L4 KV-Cache Latency

Latency signature:

TPOT rises and is spiky (and TTFT rises if admission is blocked).¶

Trace:

The L4 queue span grows; decode iterations show preemption or recompute gaps.¶

L4 engine metrics:

KV-cache utilization is near capacity; preemption and swap counters rise; waiting requests rise.¶

L1 device metrics:

Not necessarily saturated; utilization may drop during preemption and recompute churn.¶

Isolation test:

Replay with reduced maximum concurrent sequences or a larger KV budget. If the TPOT spikes disappear, L4 is confirmed.¶

Illustrative trigger:

KV-cache utilization greater than 90% with non-zero preemptions per minute.¶

Remediation:

Enable and size prefix caching; quantize the KV cache (for example, FP8); tune batch and admission limits; use chunked prefill or prefill/decode disaggregation; add replicas.¶

7.3.3. L1 HBM Bandwidth Saturation

Latency signature:

TPOT rises smoothly, tracking batch size and context length.¶

Trace:

The L4 decode span grows uniformly per step; there is no extra queueing.¶

L4 engine metrics:

KV-cache usage may be moderate; the running batch is large; tokens/s per GPU plateaus.¶

L1 device metrics:

DRAM activity (memory bandwidth utilization) stays near its ceiling during decode; tensor-pipe activity is comparatively low.¶

Isolation test:

Replay at a fixed batch with growing context length or batch size. If TPOT scales roughly with bytes read per step while DRAM activity stays pinned, L1 is confirmed.¶

Illustrative trigger:

DRAM activity greater than 0.8 sustained during decode windows.¶

Remediation:

Quantize weights or KV cache to reduce bytes per token; use speculative decoding (more tokens per weight read); use GQA/MQA models (L3); scale out via tensor parallelism; move to higher-bandwidth memory parts.¶

7.4. Troubleshooting Matrix

Each entry gives the symptom, the suspected layer, the telemetry to inspect, an isolation test, and a remediation.¶

  1. Response arrives all at once despite streaming being requested. Layer: L7/L6. Telemetry: client timing of first byte versus first rendered chunk; proxy logs. Test: call L6 directly, bypassing CDN or proxy. Remediation: disable response buffering on proxies; use streaming-compatible output guardrails.¶

  2. Client timeouts while the server reports success. Layer: L7. Telemetry: client versus server span durations. Test: compare the client timeout with server p99 E2E latency. Remediation: align timeouts with the SLO; implement cancellation propagation.¶

  3. TTFT high, with constant overhead across all prompts. Layer: L6. Telemetry: gateway and guardrail spans. Test: disable the guardrail chain in a test route. Remediation: parallelize guardrails; use smaller classifier models; cache policy verdicts.¶

  4. Prompt token count grows with each conversation turn. Layer: L6. Telemetry: Enriched Prompt token count per request. Test: replay with history truncated. Remediation: history summarization, windowing, or memory retrieval instead of full replay.¶

  5. TTFT high only for grounded requests. Layer: L5. Telemetry: L5 span breakdown (embed, search, rerank). Test: replay with retrieval bypassed (Section 7.3). Remediation: index residency, co-location, embedding cache, lower k.¶

  6. Grounded answers cite wrong or stale sources. Layer: L5. Telemetry: retrieval evaluation (recall@k); index freshness. Test: query a known-answer set against the index. Remediation: re-chunk; re-embed with a matched model; refresh the index; add a reranker.¶

  7. TTFT high under load but low at idle. Layer: L4. Telemetry: queue-time span; waiting-request gauge. Test: replay at reduced concurrency. Remediation: autoscale replicas; priority classes; admission control.¶

  8. Intermittent TPOT spikes. Layer: L4. Telemetry: KV-cache utilization; preemption and swap counters. Test: reduce concurrency or increase the KV budget (Section 7.3). Remediation: prefix caching, KV quantization, chunked prefill, disaggregation.¶

  9. Low prefix-cache hit rate despite a shared system prompt. Layer: L6 to L4. Telemetry: prefix-cache hit rate; prompt diffs. Test: compare tokenized prefixes across requests. Remediation: make L6 templates deterministic; place variable content after the shared prefix.¶

  10. Quality regression after deployment with normal latency. Layer: L3. Telemetry: evaluation-suite deltas; logit entropy; quantization configuration. Test: A/B against reference-precision weights. Remediation: revisit the quantization scheme; verify the chat template and RoPE scaling.¶

  11. NaN or garbage output on long contexts. Layer: L3/L2. Telemetry: logit NaN/Inf checks; activation statistics. Test: run the same input at higher precision. Remediation: change precision for unstable operations; verify the context-length configuration.¶

  12. Latency jitter after a model or framework upgrade. Layer: L2. Telemetry: compilation and recompilation logs; profiler timeline. Test: warm up and replay with fixed shapes. Remediation: eliminate graph breaks; shape bucketing; CUDA Graphs.¶

  13. Low GPU utilization at small batch with high latency. Layer: L2. Telemetry: profiler view of CPU launch gaps between kernels. Test: profile one decode step. Remediation: CUDA Graphs; kernel fusion; larger effective batch.¶

  14. Multi-GPU replica slower than expected. Layer: L2/L1. Telemetry: collective timing; NVLink/InfiniBand throughput counters. Test: run collective benchmarks on the node. Remediation: topology-aware placement; adjust parallel degrees; repair degraded links.¶

  15. TPOT rises smoothly with batch size and context length. Layer: L1. Telemetry: DRAM activity; tensor-pipe activity. Test: fixed-batch context sweep (Section 7.3). Remediation: quantization; speculative decoding; scale-out; higher-bandwidth parts.¶

  16. Throughput drops after sustained load. Layer: L1. Telemetry: power versus cap; temperature; clock-throttle reasons. Test: correlate the drop with throttle events. Remediation: cooling remediation; power-cap policy; load spreading.¶

  17. Sporadic request failures on one node. Layer: L1. Telemetry: Xid and ECC error counters; driver logs. Test: drain the node and run device diagnostics. Remediation: replace or reset the device; exclude the node from scheduling.¶

7.5. Layer-by-Layer Triage Procedure

Diagnosis SHOULD proceed top-down for attribution and bottom-up for confirmation:¶

  1. Define the symptom quantitatively, as a change in TTFT, TPOT, E2E, error rate, goodput, or quality, with percentile and time window.¶

  2. Decompose the latency (Section 7.2). Determine whether TTFT, TPOT, or both moved.¶

  3. Walk the trace top-down (L7 to L4). Compare span durations per layer against a baseline window. The first layer whose span distribution shifted is the candidate layer.¶

  4. Check the boundary data state. Verify that the data state entering the candidate layer is unchanged (for example, prompt token count at L6/L4, k and chunk sizes at L5/L6, batch size at L4/L3). A changed input implicates the layer above.¶

  5. Correlate with lower-layer telemetry (L4 metrics, then L2 profiles, then L1 counters), joining on time, replica, node, and device identifiers.¶

  6. Run the isolation test for the candidate layer, changing exactly one variable.¶

  7. Confirm bottom-up. Ensure that the lower layers are healthy under the isolation test, ruling out a masked L1 or L2 cause.¶

  8. Remediate at the owning layer, then re-measure against the original symptom definition.¶

  9. Record the incident with its AOSI layer attribution, enabling layer-level reliability metrics over time.¶

8. Future Work

The following extensions are reserved. They are informative in this revision and may be specified in future documents.¶

8.1. Layer 8: Agentic Workflows

Scope: self-correcting planning and multi-agent orchestration above L7, that is, agents that decompose goals into plans, invoke tools, observe results, critique and revise, and coordinate with other agents.¶

Open questions:¶

  • The canonical data state for L8 (candidate: "Plan Graph" or "Task State"), and how it maps onto multiple L7 requests.¶

  • Boundaries between L8 planning and L6 orchestration (tool routing, memory).¶

  • Observability: trace models for long-running, branching, multi-agent executions; attribution of cost and latency to plan steps.¶

  • Security: authority delegation, tool-permission scoping, loop and runaway-cost controls, and inter-agent trust.¶

8.2. Layer 9: Distributed Inference and Federated Learning

Scope: cross-region and federated serving and learning, that is, inference spanning multiple clusters or regions, disaggregated prefill and decode across sites, edge-cloud split execution, and federated learning or adaptation where data cannot leave its jurisdiction.¶

Open questions:¶

  • Whether L9 is a layer or a cross-cutting plane that spans L1-L4 across sites.¶

  • Data states for cross-site KV-cache transfer and federated parameter updates.¶

  • Data residency and regulatory constraints as first-class architectural inputs.¶

  • Consistency, failover, and model-version coherence across regions.¶

8.3. Global Optimization

Scope: a cross-layer optimization plane targeting energy efficiency and low-latency token delivery, through joint tuning of L6 routing, L4 scheduling, L3 precision, L2 compilation, and L1 power and placement against SLOs and energy budgets.¶

Open questions:¶

  • Common metrics (for example, energy per output token and goodput per watt) and how to measure them consistently across layers.¶

  • Feedback interfaces from L1 telemetry to L4 and L6 control decisions.¶

  • Guardrails ensuring that global optimization does not violate per-layer security or quality constraints.¶

9. Related Work

AOSI is not the first layered description of AI systems, and it is not intended to replace any of the works below. This section records the prior work the model builds on, how AOSI relates to each, and what AOSI does and does not claim as new.¶

9.1. Layered Reference Models and AI Standards

OSI Basic Reference Model [ISO7498-1] [X.200]:

AOSI borrows its method from OSI: a fixed number of layers, a service boundary between adjacent layers, a named data unit at each boundary, and a model that is not intended to serve as an implementation specification. AOSI applies that method to a different domain (generative AI execution on one or more accelerators). It does not define wire protocols, and it is not an extension of OSI.¶

ISO/IEC 22989 [ISO22989]:

This document sets out vocabulary and concepts for AI. AOSI does not redefine general AI terms. Where a term in Section 2.2 overlaps with ISO/IEC 22989, the ISO/IEC definition takes precedence, and future revisions of this document are expected to align their terminology with it.¶

ISO/IEC 23053 [ISO23053]:

This document describes the components and functions of ML-based AI systems in a technology-neutral way, covering the whole ML system. AOSI is narrower and more operational: it covers inference-time execution of generative models, splits that execution into seven layers from the API payload down to device execution, and names the data state at each boundary. ISO/IEC 23053 helps describe what an ML system consists of; AOSI helps locate where in the serving path a behaviour, cost, or fault occurs.¶

NIST AI RMF and Generative AI Profile [NIST-AI-RMF] [NIST-AI-600-1]:

These are organizational risk-management frameworks (Govern, Map, Measure, Manage), not technical layer models. AOSI complements them by giving a technical location for the measurements and controls that the RMF calls for. For example, the Measure and Manage activities for a retrieval system can be scoped to L5.¶

9.2. Industry AI and LLM Stack Models

Emerging Architectures for LLM Applications [A16Z-LLM]:

This reference architecture describes the components of an LLM application: data pipelines, embedding models, vector databases, orchestration, APIs and plugins, LLM caches, logging and validation, and app hosting. Its focus is the application tier, which roughly corresponds to AOSI L5-L7. It does not break down serving, model, framework, or hardware tiers, and it does not define boundary data states.¶

MLOps continuous delivery [GOOGLE-MLOPS]:

This reference describes MLOps maturity levels and pipeline components for training, validating, and deploying models. It is organized around the ML lifecycle, not around the layers that one inference request passes through. AOSI's out-of-scope training concerns are where lifecycle models such as this apply.¶

MLPerf Inference [MLPERF-INF]:

This is a benchmark suite, not a layer model. It measures system-level inference performance that, in AOSI terms, depends jointly on L1-L4. AOSI's latency decomposition is intended to explain which layer drives a benchmark result.¶

Serving-system research [PAGEDATTENTION]:

Work such as PagedAttention shows that bottlenecks at the serving tier (KV-cache memory management) can dominate throughput. That evidence supports treating L4 as a layer distinct from L3 (model architecture) and L1 (memory hardware).¶

MITRE ATLAS [MITRE-ATLAS] is a knowledge base of adversary tactics and techniques against AI-enabled systems. NIST AI 100-2 [NIST-AML] gives a taxonomy and terminology of adversarial machine-learning attacks and mitigations. Both describe what an adversary does; AOSI adds where the technique materializes, so that detection and controls can be placed at a specific layer under principle P7.¶

The Secure AI Framework [SAIF] is a conceptual framework of security practices for AI systems. AOSI is compatible with it and can serve as the layer index for mapping SAIF-style controls.¶

9.4. Other OSI-Inspired AI Layer Models

Conceptual Framework for Autonomous Cognitive Entities [ACE]:

A six-layer cognitive architecture for autonomous agents, running from an Aspirational Layer down to Task Prosecution. It layers an agent's reasoning and control, not the execution path of a request. It is relevant to the future L8 (Agentic Workflows).¶

OSI-Inspired Stack for Agentic AI [OSI-AGENTIC]:

A seven-layer interoperability stack for multi-agent systems, from physical infrastructure and runtime up to agent-to-agent communication, coordination, and governance. Its main concern is interoperability between agents; AOSI's concern is the execution path within one generative inference request.¶

AOSI does not claim to be the first OSI analogy for AI. Its scope (single-request generative inference execution) and its emphasis on boundary data states and diagnostics distinguish it from these models.¶

9.5. Contribution and Limitations

On the evidence reviewed above, AOSI claims the following specific contributions:¶

  1. An end-to-end, named data-state chain for generative inference (Section 4.3). None of the works reviewed define a named data state at every boundary from the API down to the device.¶

  2. A full-depth split of the serving path, placing the application, orchestration, retrieval, serving, model, framework/compiler, and hardware tiers in one ordered stack. Industry stack diagrams usually stop at the model API (application view) or start at the accelerator (infrastructure view).¶

  3. Per-layer diagnostics (Section 7): a layer-isolation method and a troubleshooting matrix that attribute latency and failures to a single layer, with proposed telemetry attributes (Appendix B).¶

  4. Cross-layer security placement (Section 11): each threat is assigned to the layer where it materializes, turning existing threat catalogues into a layer-indexed control map.¶

Limitations: AOSI is a conceptual, informational model. It has not been adopted or endorsed by ISO/IEC, ITU-T, the IETF, NIST, or any other body. Its layer boundaries have not yet been validated empirically across many production deployments. Training pipelines are out of scope for this revision. Counter-examples, overlapping prior art, and evidence for or against each claim are welcome.¶

10. Applying the Model

AOSI is intended for the following uses. None constitutes certification.¶

Architecture design and review:

Describe a system by listing the components occupying each layer and the data states at each boundary; identify missing layers (for example, no L5 integrity controls) and cross-layer couplings (P3).¶

Observability design:

Instrument boundaries and tag spans with aosi.layer (Appendix B) so that the method in Section 7 can be executed.¶

Incident management:

Classify incidents by AOSI layer to identify recurring weak layers.¶

Security architecture:

Map threats and controls per Section 11 and verify defense in depth.¶

Education:

Provide a common vocabulary across application, platform, ML, and infrastructure roles.¶

A description of a system claiming AOSI alignment SHOULD include: (a) the component inventory per layer; (b) the boundary data states; (c) the telemetry emitted per layer; (d) the security controls per layer; and (e) any documented cross-layer couplings.¶

11. Security Considerations

This document defines a conceptual reference model and no protocol; it introduces no new security mechanisms. However, a principal use of the model is to place security controls. Consistent with principle P7, AOSI places each threat at the layer where it materializes; controls at adjacent layers provide defense in depth.¶

L7 (Application):

Threats: direct prompt injection and jailbreak attempts; session hijacking; abuse and automation; leakage of sensitive output to unauthorized users. Controls: strong end-user authentication; input size limits; abuse detection; output rendering that does not execute untrusted content (for example, HTML/Markdown sanitization).¶

L6 (Orchestration and Gateway):

Threats: prompt injection (direct, and indirect via tool or retrieved content); system-prompt disclosure; insecure tool or function invocation; quota bypass; cross-tenant state leakage. Controls: a policy enforcement point with input and output guardrails; strict separation of system, user, and retrieved content; least-privilege tool scopes; per-tenant session isolation; audit logging.¶

L5 (Retrieval and Knowledge):

Threats: data poisoning of the corpus or index; indirect prompt injection embedded in documents; ACL bypass leading to unauthorized retrieval; embedding inversion leaking source text. Controls: provenance and integrity checks on ingested documents; ACL-filtered retrieval enforced server-side; content scanning for injected instructions; access control on the vector store; encryption at rest.¶

L4 (Inference and Serving):

Threats: model extraction via high-volume querying; cross-request leakage through shared prefix or KV caches (timing side channels); denial of service via long prompts or unbounded generation. Controls: rate limiting and anomaly detection; per-tenant cache isolation or partitioning where confidentiality requires it; token and time budgets; a policy on exposure of log-probabilities.¶

L3 (Model and Weights):

Threats: backdoored or tampered weights; membership inference and training-data extraction; unsafe behaviour introduced by fine-tuning or adapters. Controls: signed and hash-verified model artifacts; model provenance (supply-chain attestation); red-team evaluation before promotion.¶

L2 (Framework and Runtime):

Threats: supply-chain compromise of frameworks, kernels, or compilers; unsafe deserialization of model files. Controls: pinned and verified dependencies; software bills of materials; safe serialization formats (for example, safetensors); isolated build pipelines.¶

L1 (Physical Infrastructure):

Threats: hardware side channels (timing, power, memory residue between tenants); firmware compromise; physical access. Controls: device isolation (dedicated devices or hardware partitioning); memory scrubbing between tenants; firmware attestation and updates; confidential-computing capabilities where available; physical security.¶

Implementations claiming AOSI alignment SHOULD document, per layer, which threats are in scope and which controls are applied, and MUST NOT rely on a single layer (for example, L6 guardrails alone) as the sole control for threats that materialize at L5 or below.¶

The telemetry recommended in Section 7 and Appendix B can itself expose sensitive information (prompt sizes, tenant identifiers, retrieval provenance, and timing that may enable side-channel inference). Telemetry pipelines SHOULD apply the same access control and data-minimization policies as the request data they describe.¶
